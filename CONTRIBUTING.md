# Contributing

This is a single-maintainer hobby project — one person's desk sign, built and
kept up by Alan Young (cheeseprince) in spare time. Issues and pull requests
are genuinely welcome, but there is no team behind this repository and no
schedule for review. A small fix might land in a day; anything larger will
sit until there is time for it.

## Reporting a bug

Open a [GitHub Issue](https://github.com/cheeseprince/caltrain-notifier/issues).
A report that can actually be acted on includes:

- **Which board revision you're on — v2.0 or v2.2.** The two swap `TFT_MISO`
  and `TOUCH_CS`, they build from different PlatformIO environments
  (`caltrain` vs `caltrain_v20`), and a bug specific to one revision is
  unreproducible without knowing which. See the README's
  [Board revisions](README.md#board-revisions-matter--build-the-one-that-matches-your-unit)
  section if you're not sure which you have.
- **The `[BUILD]` and `[CHIP]` lines from the serial monitor.** `src/main.cpp`
  prints both on every boot for exactly this reason — they identify the
  firmware version, build date, and the actual silicon (module, flash size)
  of the unit that misbehaved.
- **The relevant serial output** around the failure — not the whole log, but
  enough to show what the device was doing when it went wrong.

Without those three, a report is usually just "it didn't work," which cannot
be turned into a fix.

## Reporting a vulnerability

Do not use a GitHub Issue for a security problem. Follow
[SECURITY.md](SECURITY.md) instead — it explains what's in scope and how to
report privately.

## Contributing a change

Standard GitHub flow: fork, branch, pull request.

Before starting anything nontrivial, open an issue first to discuss the
change. This is a single-maintainer project — there is no design review
happening in your head that matches the one in mine, and a pull request built
on a wrong assumption about scope or approach is wasted work on both sides.
Small, obvious fixes (a typo, a broken link, an off-by-one) don't need this;
a new feature, a behavior change, or anything touching the OTA or credential
paths does.

## Testing policy

This project follows a policy in practice, and it applies to new
contributions too:

- **Pure logic lives in host-testable modules.** Anything that touches
  Arduino, WiFi, NVS, or the panel sits behind an `#ifdef ARDUINO` seam
  instead of being tested on the host — see the `src/` layout in the
  [README](README.md#layout) for which files are which. If your change adds
  logic that *can* be pulled out from behind that seam, it should be.
- **New functionality with testable logic gets a host test.** There are 12
  host test binaries that run under `cd test && make`, plus a libFuzzer
  target for the one function that parses bytes from outside
  (`src/siri_parse.cpp`, built with `make fuzz`). A pull request that adds
  logic with no corresponding test in `test/` will be asked for one before
  it merges.
- **Tests are mutation-checked.** After a test passes, the implementation it
  covers is deliberately broken to confirm the test actually fails. A test
  that stays green against broken code is not testing anything — it's
  decoration. This isn't aspirational: `7a8aeb7` ("test: close two
  mutation-check gaps in ota_manifest coverage") is a real commit that
  records exactly which assertions didn't die when they should have, and
  fixes them. A new test should be able to point at the line it would have
  caught.

## Build and test commands

Straight from the README, so they can't drift out of sync with it:

```bash
cd test && make       # host tests — no board, no network
pio run -e caltrain        # device build, board revision 2.2
pio run -e caltrain_v20    # device build, board revision 2.0
```

## Coding conventions

- **C++17.**
- Host tests build warning-free under `-Wall -Wextra -Werror`
  (`test/Makefile`). A change that introduces a warning fails CI, not just a
  local build.
- `platformio.ini` pins the platform and every library to an exact version —
  `espressif32@7.0.1`, `bodmer/TFT_eSPI@2.5.43`, no carets. Dependabot has no
  PlatformIO ecosystem, so nothing proposes these bumps automatically; if a
  pull request needs a newer version of either, say so explicitly and expect
  it to require a device build, not just a host-test pass.
- `src/stations.h` and `src/timetable_data.h` are generated by
  `tools/gen_stations.py` and `tools/gen_timetable.py` from the Caltrain GTFS
  feed. Never hand-edit them — regenerate from the feed instead, per the
  README's [Keeping the timetable current](README.md#keeping-the-timetable-current).
- Comments explain *why*, not what the next line of code already says. Match
  the existing style in the file you're touching before adding your own.

## What CI checks

Every push and pull request runs six required jobs
(`.github/workflows/ci.yml`): a checksum-pinned secret scan, timetable
freshness, the host test suite, a device build for each board revision
(`caltrain` and `caltrain_v20`), and a bounded fuzz smoke test against
`siri_parse.cpp`. A pull request cannot merge until all six are green.
